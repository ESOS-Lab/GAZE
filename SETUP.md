# GAZE Artifact Setup

This document lists every OS-level dependency and one-time system
configuration change needed to build and run the experiments in
`experiment_script/`. All of it is automated by `setup_env.sh` at the repo
root — this file explains *what* that script does and *why*, for anyone who
needs to review, adapt, or manually replay the steps.

## Environment this was built/tested on

- Ubuntu 24.04.4 LTS, kernel build target `6.1.0`
- x86_64, 40 logical CPUs, 512 GB RAM (not a hard requirement — see
  "Resource use" below for per-experiment numbers)
- apparmor enabled (Ubuntu default)

## Components

| Path | What it is | Needs building? |
|---|---|---|
| `kernel/` | Linux 6.1 tree with GAZE/F2FS filesystem modes | Yes — `./kernel/switch_mode.sh <mode>` then `./kernel/build_kernel.sh` |
| `kernel/f2fs-tools-1.15.0/` | `mkfs.f2fs`, used in place (no `make install`) by `config.sh`'s `MKFS_F2FS` | Yes — `setup_env.sh` builds it (source only, binary is gitignored) |
| `scalelfs-mkfs-tools/` | traditional f2fs-tools 1.16.0 (ScaleLFS's own mkfs), used in place via `MKFS_SCALELFS` | Yes — `setup_env.sh` builds it (or run its `build_tools.sh`) |
| `ssd_emulator/` | NVMeVirt SSD emulator (kernel module) | Yes — `./ssd_emulator/run_nvmevirt.sh` |
| `benchmarks/fio_src`, `benchmarks/tpcc` | fio and tpcc-mysql, prebuilt binaries committed | No |
| `benchmarks/filebench` | Filebench, source only (binary is gitignored) | Yes — `setup_env.sh` builds it |
| `benchmarks/YCSB` | YCSB, source + prebuilt `core`/`jdbc` module jars | Partial — `setup_env.sh` fills in one missing dependency set |
| `experiment_script/` | Per-workload run scripts + shared config (`config.sh`) | No |
| `experiment_script/general_resource/plot/*.gpi` | gnuplot scripts for post-experiment graphs | No — run manually with `gnuplot`/`gv` after an experiment finishes; not invoked by any run script |

## 1. Install with `setup_env.sh`

```
./setup_env.sh
```

Requires passwordless sudo (or will prompt for a password if run under a
normal sudo account). It is idempotent — re-running it only fixes what's
out of date. It performs:

### OS packages (apt)
- Kernel/ssd_emulator build toolchain: `build-essential bison flex
  libssl-dev libelf-dev bc libncurses-dev dwarves pkg-config`
- Filebench + f2fs-tools build toolchain: `autoconf automake libtool
  uuid-dev libselinux1-dev`
- MySQL / YCSB / TPC-C toolchain: `mysql-server openjdk-11-jdk maven
  python-is-python3`
- Post-experiment graphing: `gnuplot gv` (see "Filebench build" note below —
  not invoked by any script, but needed to actually use `plot/*.gpi`)

### Filebench build
The checked-in `aclocal.m4`/`configure` may have been generated by a
different `automake` version than the one `apt` installs on this OS,
which makes plain `make` fail with:
```
configure.ac:7: error: version mismatch. This is Automake X, but the
definition used by this AM_INIT_AUTOMAKE comes from Automake Y.
```
`setup_env.sh` regenerates them locally (`libtoolize && aclocal &&
autoheader && automake --add-missing && autoconf`) before running
`./configure && make`. The resulting `filebench` binary is intentionally
gitignored (build output), so this step always needs to run on a fresh
clone.

### f2fs-tools build
Same situation as filebench: `kernel/f2fs-tools-1.15.0/configure` and
`Makefile` are gitignored build output, not checked in. `setup_env.sh` runs
its `./autogen.sh` (aclocal/autoheader/autoconf/libtoolize/automake) then
`./configure && make`. Nothing gets `make install`ed — `config.sh`'s
`MKFS_F2FS` points directly at
`kernel/f2fs-tools-1.15.0/mkfs/mkfs.f2fs` in place.

The same applies to `scalelfs-mkfs-tools/` (ScaleLFS's traditional
f2fs-tools 1.16.0): `setup_env.sh` builds it in place via its
`build_tools.sh`, and `config.sh`'s `MKFS_SCALELFS` /
`MKFS_SCALELFS_LIB` point straight into the tree. Only the `scalelfs`
baseline uses it.

### ssd_emulator memory reservation (GRUB, needs a reboot)
`ssd_emulator/insmod.sh` memory-maps a fixed physical address range to back
NVMeVirt's emulated SSD (`memmap_start`/`memmap_size`). The kernel must
reserve that exact range at boot with a `memmap=` cmdline parameter, or
`insmod` will fail or misbehave. On this NUMA machine that range is also
sized to cover an entire NUMA node (`numactl --hardware`: node 1, odd CPUs,
~258GB), with that node's CPUs isolated via `isolcpus=`, so the emulator's
threads (`insmod.sh`: `cpus=37,39`) never take a remote-memory-access hit.

`setup_env.sh` derives the required `memmap=` value directly from
`insmod.sh` (single source of truth) and, if `/etc/default/grub` doesn't
already have it, prompts before writing it and running `update-grub` — it
never does this non-interactively or without asking, and it never reboots
for you.

**This is a machine-wide change**: `GRUB_CMDLINE_LINUX` applies to *every*
kernel entry in the boot menu, not just this one. On a shared machine with
other kernels in active use, coordinate with whoever else is using it —
each of them needs to comment `GRUB_CMDLINE_LINUX` back out (and
`update-grub`) when booting their own kernel, since it isn't safe to assume
this is a GAZE-dedicated machine. On different hardware, `insmod.sh`'s
`memmap_start`/`memmap_size`/`cpus` and the `isolcpus` list are NOT
portable as-is — recompute them from that machine's own `numactl
--hardware` output (a node's memory start/size → `memmap`, that node's CPU
list → `isolcpus`, a couple of them → `insmod.sh`'s `cpus=`).

A reboot is required after `update-grub` for the reservation to take
effect — this pairs naturally with `build_kernel.sh`'s own "REBOOT
REQUIRED" step, so there's normally only one reboot needed, not two.

### MySQL configuration
Experiments run MySQL against `$MNT/mysql` (a mount point that
`experiment_script/general_resource/setup_fs.sh` formats fresh before every
run), not the package default `/var/lib/mysql`. Two things need to change
for that to work, both handled by the script from
`experiment_script/general_resource/mysqld.cnf.template`:
- `/etc/mysql/mysql.conf.d/mysqld.cnf`: `datadir = $MNT/mysql`,
  `skip-log-bin` (keeps DB size fixed across runs), `innodb_buffer_pool_size
  = 256M` (kept small deliberately — experiments measure storage I/O, not
  MySQL's own cache hit rate).
- `/etc/apparmor.d/usr.sbin.mysqld`: the "Allow data dir access" rule is
  rewritten from `/var/lib/mysql/**` to `$MNT/mysql/**`, then apparmor is
  reloaded. Without this, mysqld fails to start against the new datadir —
  apparmor denies it silently unless you check `dmesg`/journalctl for
  `DENIED` entries.

The script also adds the current user to the `adm` group (needed to read
`/var/log/kern.log` for the GC-profiling experiment path), and disables
`mysql.service` from auto-starting at boot — the experiment scripts
start/stop it themselves around each run, and starting it automatically
before `$MNT/mysql` is populated will fail (`MySQL data dir not found`,
harmless but noisy).

### YCSB
YCSB ships two launchers: `bin/ycsb` (Python) and `bin/ycsb.sh` (POSIX
shell). **Use `bin/ycsb.sh`** — the run scripts in `experiment_script/`
already do. `bin/ycsb` is written in Python 2 syntax (`except X, err:`) and
will not even parse under Python 3, and this artifact's environment has no
Python 2 available (Ubuntu dropped it after 20.04). `bin/ycsb.sh` needs no
Python at all, only `java`.

`bin/ycsb.sh` doesn't support a `-cp <jar>` flag the way the Python
launcher does, so the MySQL JDBC connector jar is added via YCSB's own
supported extension point, `bin/setenv.sh` (created by `setup_env.sh`, not
a modification to YCSB itself):
```sh
CLASSPATH="$CLASSPATH:$YCSB_HOME/mysql-connector-j-8.0.33.jar"
```

Separately, this artifact's vendored `core` module target/ directory was
missing its own dependency jars (`htrace-core4`, etc. — causes
`NoClassDefFoundError: org/apache/htrace/core/Tracer$Builder` at runtime).
`setup_env.sh` detects and fills this with a narrowly-scoped
`mvn dependency:copy-dependencies -pl core` (needs network access; does not
touch or rebuild the other ~50 already-built DB binding modules under
`benchmarks/YCSB/`).

## 2. Configure

Run `./set_config.sh [paper|auto|manual]` (no argument = menu, Enter picks
`paper`):

- **paper** (default) — the paper machine's exact sizing (255G emulated
  SSD, 64G host DRAM) and the paper's workload parameters, restored
  verbatim from `general_resource/paper_params.sh`. Needs ≥ 320G RAM;
  refuses (and points at `auto`) otherwise.
- **auto** — detects this machine's RAM/NUMA topology, derives the largest
  emulated SSD that fits, and scales the dataset knobs (FIO file size,
  fileserver file count, YCSB record/op counts, TPC-C warehouses)
  proportionally to SSD size; durations/threads/block sizes stay the
  paper's. Note: TPC-C/YCSB cold data must be regenerated at the new scale
  (see below).
- **manual** — answer every sizing question yourself; workload parameters
  are left untouched.

All modes then ask the machine-specific questions and write `.config`
(hand-editable afterwards):
- `CONV_PART` / `CONV_DEV` — this machine's actual conventional-SSD
  partition. `general_resource/setup_fs.sh` refuses to run and prints the
  exact `fdisk` command needed if `CONV_PART` doesn't exist — it
  deliberately never creates partitions automatically.
- `ZNS_DEV` / `ZNS_DEV_NAME` — auto-detected and rewritten by
  `ssd_emulator/run_nvmevirt.sh` each time the emulator loads; no need to
  set these by hand.
- `MYSQL_DATA_PATH` — directory holding pre-loaded cold MySQL data for
  TPC-C/YCSB (see below).
- `MYSQL_USER` / `MYSQL_PASSWD` — must match whatever account exists inside
  that cold data's own `mysql.user` table (each cold-data directory is a
  full, independent MySQL datadir copy with its own accounts).

### If you don't have pre-built cold MySQL data

The TPC-C/YCSB scripts assume `$MYSQL_DATA_PATH` already contains
ready-to-use MySQL datadir copies plus cold filler files (see
`run_tpcc.sh`/`run_ycsba.sh`: they `cp` these into `$MNT` before every run
instead of loading from scratch each time, since loading is slow). On a
machine without them, those benchmarks **refuse to run** (with a message)
until the data exists — everything else runs normally.

**Generate it with `experiment_script/make_cold_data.sh`** (interactive):
it sizes the datasets to your current config (record/warehouse counts from
`experiment_params.sh`, filler sizes from `SSD_GB` — already scaled if you
used `set_config.sh auto`), asks where to put them, refuses to overwrite
anything that already exists (delete conflicting files yourself first),
verifies the destination has enough free space, and shows exactly what it
will create (names, sizes, total) for confirmation before starting. The
MySQL loads run on the emulated SSD and are copied out — the paper-sized
YCSB load takes hours; scaled-down ones proportionally less. The generated
names and location are recorded in `.config` so the run scripts find them.

The manual equivalent of what it automates, for reference:

```sh
sudo systemctl start mysql   # datadir must exist and be non-empty first;
                              # setup_fs.sh + an empty mkfs.f2fs mount is enough
mysql -u root -e "
  CREATE USER '$MYSQL_USER'@'%' IDENTIFIED BY '$MYSQL_PASSWD';
  GRANT ALL PRIVILEGES ON *.* TO '$MYSQL_USER'@'%';
  FLUSH PRIVILEGES;
  CREATE DATABASE ycsb;"
cd benchmarks/YCSB
sudo bin/ycsb.sh load jdbc -P workloads/workloada -P db.properties
sudo systemctl stop mysql
# copy $MNT/mysql elsewhere as your new $MYSQL_DATA_PATH/<name> for reuse
```

## 3. Build and run

```sh
./kernel/switch_mode.sh gaze          # or: pgc | f2fs | zns_plus | scalelfs | ... (no sudo
                                       #   needed — just edits files this user already owns)
./kernel/build_kernel.sh         # reboot if it says a reboot is required
sudo reboot                           # only if the above said so
./ssd_emulator/run_nvmevirt.sh        # picks zns/conv emulation from the FS mode
                                      #   (or force one: ./run_nvmevirt.sh [zns|conv])

cd experiment_script/FIO && sudo ./run_fio.sh
cd experiment_script/Fileserver && sudo ./run_fileserver.sh
cd experiment_script/TPC-C && sudo ./run_tpcc.sh
cd experiment_script/YCSB-A && sudo ./run_ycsba.sh
cd experiment_script/YCSB-F && sudo ./run_ycsbf.sh
```

`build_kernel.sh` makes the kernel it just built the *persistent* default
boot entry (`grub-set-default`, requires `GRUB_DEFAULT=saved` +
`GRUB_SAVEDEFAULT=true` in `/etc/default/grub` — `setup_env.sh` sets these).
Every reboot boots that kernel from then on, not just the next one — until
either this script runs again with a different mode, or someone manually
picks a different entry at the boot menu, which becomes the new persisted
default in their turn. This only matters if you're not already running the
kernel version `build_kernel.sh` just installed (it prints `REBOOT
REQUIRED` when that's the case).

Before touching GRUB the script prompts for confirmation and, on yes,
also sets `GRUB_TIMEOUT=5` (backing up `/etc/default/grub`) so the boot
menu stays visible long enough for another user on the machine to pick a
different kernel. Decline the prompt to leave GRUB entirely untouched.

### Switching modes without rebuilding

All modes except `zns_plus` and `--profile` run on the *same* kernel image
(`6.1.0.sosp26_ae`) and differ only in which filesystem module gets loaded.
After one full `build_kernel.sh` + reboot, run

```sh
sudo ./kernel/build_all_modules.sh    # builds every module-only mode's .ko once
```

and from then on switch modes with `experiment_script/select_fs.sh` alone —
no rebuild, no reboot. `zns_plus` (block-layer copy-offload,
`6.1.0.sosp26_ae_copy`) and `--profile` variants still change the kernel
image itself, so they keep the switch_mode.sh → build_kernel.sh → reboot flow.

### The scalelfs baseline

`scalelfs` (fs/scalelfs, mounted as fs type `scalelfs`) is special in three ways:

- It runs on the emulated SSD in **conventional** (non-zoned) mode, using a
  dedicated 970PRO-class TLC profile (single FTL partition, 8ch × 4LUN,
  ~32MB device-GC reclaim unit — originally imported from a
  scalelfs-dedicated NVMeVirt tree, now fully integrated into
  `ssd_emulator/`; nothing outside the repo is needed). Every other mode
  needs `zns`
  (WD_ZN540 profile). **Switching is automatic**: each benchmark's
  `setup_fs.sh` reloads NVMeVirt into whatever mode its filesystem needs,
  so scalelfs and the ZNS modes can be run back to back in any order. A
  reload resets the emulated device and every setup re-runs mkfs, so no
  on-device state leaks between filesystems. (Manual override still works:
  `./ssd_emulator/run_nvmevirt.sh [zns|conv]`.)
- Unlike the ZNS modes it needs **no separate metadata SSD**: the ZNS family
  formats `mkfs.f2fs -c $ZNS_DEV $CONV_PART` (metadata on a real conventional
  partition + data on the emulated ZNS device), while scalelfs formats the
  single emulated conventional device directly — `CONV_PART` is not involved.
- It is formatted with its own **traditional f2fs-tools 1.16.0**
  (`SCALELFS_TOOLS`, default: the vendored `scalelfs-mkfs-tools/`, overridable
  in `.config`) — *never* with `kernel/f2fs-tools-1.15.0`. `setup_fs.sh` picks
  the right mkfs per mode automatically.

Each run script self-elevates only the specific privileged operations it
needs (`systemctl`, `cp`, `chown`, `mkfs.f2fs`, sysfs/procfs writes, the
`fio`/`filebench`/`ycsb.sh` binaries themselves) rather than requiring the
whole script to run as root — see `experiment_script/general_resource/lib.sh`
(`root_write` helper) and `setup_fs.sh` for the pattern. If you're running
under a *restricted* sudoers list rather than full sudo, each of those
specific commands needs a NOPASSWD entry; grep the scripts for `sudo` to get
the exact list.

## Resource use per experiment

| Script | Runtime | Disk |
|---|---|---|
| `run_fio.sh` | ~20 min (`RUNTIME=1200`) | 180 GB test file (`FILESIZE`) |
| `run_fileserver.sh` | varies with `fileserver.f` | fileset defined in `fileserver.f` |
| `run_tpcc.sh` | ~30 min (`-r10 -l1800 -i1800`) | ~215 GB cold data copied in (`cold_40G` + `cold_20G` + tpcc dataset) |
| `run_ycsba.sh` / `run_ycsbf.sh` | depends on `OPCOUNT`/`THREAD` | ~224 GB cold data copied in |

## Known gotchas

- `mkfs.f2fs`/`mount`/`insmod` failing silently under a restricted sudoers
  account almost always means the specific command+argument pattern isn't
  in that account's NOPASSWD list — check with `sudo -n -l`.
- The same applies to the benchmark entrypoints themselves
  (`sudo ./run_fio.sh` etc., which `run_experiment.sh` uses): a restricted
  list whitelists them by **absolute path**, so a repo cloned to a new
  location is denied ("Sorry, user X is not allowed to execute ./run_fio.sh
  as root") even though the identical script is whitelisted elsewhere.
  `run_experiment.sh` checks this up front and names the exact path to add.
  Either extend the whitelist to the new clone's path (a one-level wildcard
  like `/home/aec/*/experiment_script/FIO/run_fio.sh` covers every clone
  directly under `/home/aec`), or run from an account with full sudo.
- MySQL refusing to start with `MySQL data dir not found at $MNT/mysql` is
  expected whenever `$MNT` hasn't been populated yet (before the first
  `cp` in `run_tpcc.sh`/`run_ycsba.sh`/`run_ycsbf.sh`, or after
  `setup_fs.sh teardown`) — not a configuration bug.
- `debian-5.7.flag` inside a cold-data directory doesn't mean the data
  needs MySQL 5.7; mysqld auto-upgrades the data dictionary in place on
  first start against a newer server version (logged as `Server upgrade
  from 'X' to 'Y'`), which is normal, one-time, and safe.
